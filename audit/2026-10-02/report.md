# Аудит Sigamiz — 2 октября 2026

Проект пока не готов к расширению аудитории: подтверждены риск входа в чужой аккаунт через специально переданную bot-login ссылку, обход бана через сайт, публикация точной геопозиции, неверное определение дубликатов и поломки основных действий интерфейса.

Проверены `backend`, `bot`, все семь HTML-файлов, схема данных и конфигурация запуска. В браузере открыты `/`, `/xarita`, `/publish`, `/favorites`, `/about`; основные сценарии проверены при ширине 1280 и 360 px. Сервер работал на временной копии SQLite, отправка сообщений в Telegram была отключена. Форма проверялась с синтетическим аккаунтом. Приоритет P1 означает исправить до привлечения новых пользователей; P2 — следующий этап работ.

## Логические и технические находки

### B1 — P1: забаненный автор может снова публиковать через сайт

[Бот проверяет banned_users](D:/Projects/sigamiz/bot/main.py:589), но [общий сервис](D:/Projects/sigamiz/backend/listing_service.py:150) и [API публикации](D:/Projects/sigamiz/backend/main.py:1009) этого не делают. В изолированном тесте пользователь, добавленный в `banned_users`, получил новое объявление со статусом `active`.

Исправление: проверять бан в общем сервисе непосредственно перед записью. Проверка только при начале диалога бота недостаточна: бан может появиться после начала черновика.

### B2 — P1: сайт раскрывает точные координаты, хотя обещает приблизительные

[Бот смещает точку](D:/Projects/sigamiz/bot/main.py:729), а [сайт отправляет координаты с шестью знаками](D:/Projects/sigamiz/frontend/publish.html:199). Сервис сохраняет их без смещения, [публичный ответ API](D:/Projects/sigamiz/backend/main.py:318) возвращает их напрямую. Тест подтвердил точное совпадение входных и публичных координат. Это противоречит [обещанию на About](D:/Projects/sigamiz/frontend/about.html:42).

Исправление: общая политика приватности координат. Отделить внутреннюю точку от публичной, формировать публичную точку на сервере для обоих каналов. Не применять дополнительное случайное смещение при каждом GET.

### B3 — P1: объявление определяется как дубликат самого себя

[find_similar_photo](D:/Projects/sigamiz/backend/listing_service.py:96) ищет среди всех активных объявлений, включая только что вставленное. При обработке второго фото первое уже записано. Два одинаковых фото в одном объявлении дали `hidden_pending_review`, а `duplicate_matches[0].listing_id` совпал с ID нового объявления.

Исправление: исключать текущий ID из сравнения, повтор внутри одного набора фото обрабатывать отдельно. Порог average hash также нуждается в проверке на реальных фотографиях: простые и однотонные изображения могут совпадать без связи с квартирой.

### B4 — P1: срок действия и статусы объявлений обрабатываются неверно

[Публичная выдача](D:/Projects/sigamiz/backend/main.py:540) проверяет только `status='active'`; аналогично устроен поиск бота и рекомендации. [Фоновая задача](D:/Projects/sigamiz/backend/main.py:230) запускается раз в сутки и впервые не выполняется сразу при старте. В браузере были показаны десять объявлений, срок которых уже истёк.

Кроме того, задача меняет на `expired` любые старые записи, включая `removed` и `hidden_pending_review`. Изолированный тест подтвердил все три перехода. Удалённое объявление после этого снова попадает в `/api/my-listings`, поскольку там исключён только `removed`. [Продление в боте](D:/Projects/sigamiz/bot/main.py:1388) меняет дату, но не восстанавливает статус `expired`; `/my` вообще не показывает истёкшие записи.

Исправление: единые допустимые переходы статусов, фильтр срока непосредственно в запросах, UTC для дат. Expiration должен затрагивать только определённые состояния. Продление должно иметь явные правила для активного и истёкшего объявления.

### B5 — P1 для PostgreSQL: Telegram ID хранятся в INTEGER

[Схема](D:/Projects/sigamiz/backend/schema.sql:3) использует `INTEGER` для Telegram ID в объявлениях, пользователях, банах, избранном и предпочтениях. [Конвертер PostgreSQL](D:/Projects/sigamiz/backend/db.py:49) оставляет эти поля `INTEGER`, то есть со знаковым диапазоном до 2 147 483 647. Telegram ID за пределами этого диапазона приведёт к ошибке записи в PostgreSQL. SQLite этот дефект маскирует.

Исправление: `BIGINT` для внешних Telegram ID во всех связанных таблицах и миграция существующей базы. PostgreSQL в этом аудите не запускался; типы подтверждены по результату преобразования схемы.

### B6 — P1 при параллельной публикации в PostgreSQL: правило одного объявления не защищено базой

[Сервис](D:/Projects/sigamiz/backend/listing_service.py:155) сначала делает SELECT, затем INSERT. В схеме нет уникального ограничения на владельца для статусов `active` и `hidden_pending_review`. Две транзакции PostgreSQL могут одновременно пройти SELECT. [Форма](D:/Projects/sigamiz/frontend/publish.html:228) также не блокирует кнопку на время отправки.

Исправление: частичный уникальный индекс, согласованная обработка конфликтов и защита от повторной отправки. Для перехода старого объявления в active через approve нужен тот же контроль. Это вывод по коду; конкурентный тест PostgreSQL не проводился.

### B7 — P2: сохранённый поиск теряет условия пользователя

[Поиск бота](D:/Projects/sigamiz/bot/main.py:1256) применяет пол ищущего и желаемый пол соседей, но [save_search_preferences](D:/Projects/sigamiz/bot/main.py:358) их не сохраняет. [Общий по смыслу matching](D:/Projects/sigamiz/backend/main.py:473) также не проверяет пол. После отсутствия результатов пользователь может получить уведомление о неподходящем варианте.

Предпочтения сохраняются только при нулевой выдаче. Новый поиск с найденными вариантами оставляет старую подписку. Если ранее через API сохранены университет, комнаты или тип жилья, бот не очищает эти поля: последующие уведомления продолжают учитывать невидимые старые ограничения.

Исправление: одна полная модель предпочтений и явное решение, обновляет ли каждый поиск подписку. Пол автора и требования к соседям должны быть разными полями и совпадать между выдачей и уведомлениями.

### B8 — P2: уведомления отправляются до commit и тормозят публикацию

[API](D:/Projects/sigamiz/backend/main.py:1047) и [бот](D:/Projects/sigamiz/bot/main.py:1106) отправляют сообщения до `conn.commit()`. API вызывает синхронный `requests.post` из `async def`, последовательно для каждого подписчика, с timeout 8 секунд на запрос. Пока идёт рассылка, транзакция остаётся открытой. Пользователь может получить ссылку до появления записи для другого соединения, а при ошибке commit — на несохранённое объявление. Повторной доставки нет.

После [approve](D:/Projects/sigamiz/bot/main.py:625) скрытого нового объявления рассылка вообще не запускается. Ссылка уведомления ведёт на общую карту без ID найденного варианта.

Исправление: записывать событие уведомления в одной транзакции с объявлением, затем доставлять его отдельным обработчиком с повтором и защитой от повторной доставки. Добавлять `?listing=<id>` в ссылку.

### B9 — P1 при раздельном размещении сервисов: фото находятся только на локальном диске

[Сервис фото](D:/Projects/sigamiz/backend/listing_service.py:201) пишет файл в `uploads` и сохраняет абсолютный путь. [Backend](D:/Projects/sigamiz/backend/main.py:1146) раздаёт свой локальный каталог. README предлагает отдельные Railway web и bot worker. Общий PostgreSQL не делает файловые системы этих сервисов общими: фото, загруженные ботом, будут недоступны web без общего хранилища. При разных корнях проекта также ломается [normalize_photo_path](D:/Projects/sigamiz/backend/main.py:366).

Исправление: общее постоянное хранилище и стабильный ключ/URL фотографии. На одном сервере с общим каталогом этот конкретный сценарий может работать; конфигурация продакшена в аудите не проверялась.

### B10 — P2: параллельные сообщения бота могут перезаписывать черновик

[draft_data](D:/Projects/sigamiz/bot/main.py:146) держит lock только на чтении и сохранении, отпуская его на время изменения данных. Два обработчика получают независимые копии; последний сохранённый снимок стирает изменения другого. В тесте перекрывающихся контекстов из двух фотографий осталась только одна. [Альбом фотографий](D:/Projects/sigamiz/bot/main.py:954) — конкретный сценарий такого риска.

Исправление: последовательная обработка изменений для одного пользователя либо атомарное обновление черновика в БД. Один JSON-файл дополнительно не обеспечивает согласованность нескольких процессов бота.

### B11 — P2: входные данные и ресурсы недостаточно ограничены

[parse_float_field](D:/Projects/sigamiz/backend/listing_service.py:39) принимает `NaN`: проверки min/max его не отсекают. Тест это подтвердил; дальнейшая запись может завершиться ошибкой БД. Строковые поля вызывают `.strip()` без проверки типа, предпочтения принимают произвольные значения. Ограничено количество фотографий, но не размер JSON/base64 в байтах. Фото обрабатываются и пишутся после INSERT; rollback базы не удаляет уже записанные файлы.

Исправление: типизированные модели запросов, проверка конечности координат, ограничения размера файлов и запроса, подготовка файлов до финальной записи или явная компенсационная очистка. Ошибки должны завершать транзакцию и закрывать соединение через `finally`/контекстный менеджер.

### B12 — P2: сессия не имеет проверяемого сервером срока и отзыва

[Cookie](D:/Projects/sigamiz/backend/main.py:250) содержит только ID и подпись. `max_age=90 дней` ограничивает хранение обычным браузером, но [проверка](D:/Projects/sigamiz/backend/main.py:254) не проверяет возраст токена. [Logout](D:/Projects/sigamiz/backend/main.py:724) удаляет только локальный cookie. Скопированная подпись сохраняет силу после выхода. При отсутствующем `SESSION_SECRET` генерируется случайный ключ на каждый процесс/перезапуск.

Исправление: серверный срок и версия/идентификатор сессии для отзыва, постоянный обязательный ключ в развёртывании, `Secure` для HTTPS cookie.

### B13 — P2: данные и сообщения не гарантируют возможность связаться с автором

Объявление может иметь пустой Telegram username и отсутствующий телефон: общий сервис это разрешает. [Контакты в подробностях](D:/Projects/sigamiz/frontend/map.html:724) в таком случае отсутствуют. ID автора не используется для альтернативного маршрута связи. Кроме того, [бот сообщает «опубликовано»](D:/Projects/sigamiz/bot/main.py:1037) даже если сервис сохранил объявление как `hidden_pending_review`.

Исправление: гарантировать хотя бы один согласованный с пользователем канал связи, например через бота; возвращать боту статус создания и показывать понятное сообщение об ожидании модерации.

### B14 — P2: запуск и проверка проекта плохо отделены от рабочего кода

Импорт `backend.main` сразу выполняет миграции и запускает scheduler; импорт `bot.main` запускает polling. Это осложняет изолированные проверки. В репозитории нет тестов правил публикации, поиска и статусов. Workflow деплоя проверяет запуск процессов, но не работоспособность сценариев; бот перезапускается раньше backend, хотя инициализация полной схемы находится у backend.

Исправление: вынести запуск в entrypoint/lifespan, миграции выполнять отдельным шагом перед обоими сервисами. Добавить небольшие содержательные проверки общего домена: бан, срок, один активный владелец, приватность, дубликаты и поиск.

### B15 — P1: fallback-вход через бота автоматически одобряет чужой запрос входа

[Публичный start endpoint](D:/Projects/sigamiz/backend/main.py:666) создаёт токен входа. Когда другой пользователь открывает соответствующую ссылку и отправляет `/start`, [send_welcome](D:/Projects/sigamiz/bot/main.py:566) автоматически привязывает токен к его Telegram ID без отдельного подтверждения входа на сайт. [complete endpoint](D:/Projects/sigamiz/backend/main.py:686) затем выдаёт сессию предъявителю токена. Поэтому человек, создавший ссылку, может получить сессию пользователя, которого убедил открыть эту ссылку и нажать Start.

Сценарий воспроизведён на оригинальных функциях с изолированной SQLite, двумя ролями пользователей и подменённой отправкой ответа: токен инициатора был подтверждён `/start` второго пользователя, а завершение по этому токену перешло к выдаче сессии второго пользователя. Реальные аккаунты Telegram не использовались. Для эксплуатации нужен переход пользователя по переданной ему ссылке и Start; это не удалённый вход без действий пользователя.

Исправление: не одобрять web-login при обычном `/start`. Требовать отдельное понятное подтверждение входа с контекстом и сверкой кода из инициирующего браузера либо использовать основной Telegram Login flow. Привязать завершение к исходному браузерному запросу и атомарно потреблять одноразовый токен. Само по себе добавление nonce не заменяет осознанное подтверждение пользователем.

## Дизайн, UI и UX

Основная палитра и типографика главной читаются хорошо. На мобильной главной нет горизонтального переполнения, основной переход на карту заметен. Основные проблемы находятся в рабочих сценариях, согласованности состояний и данных.

### U1 — P1: карточки карты сжимаются до полос

[CSS карточек](D:/Projects/sigamiz/frontend/map.html:102) допускает flex shrink внутри вертикального списка. На 1280×800 десять карточек имеют высоту около **35,7 px**, их медиаблоки — **0 px**, при высоте содержимого около 219 px. На 360×800 карточка имеет высоту 246 px, но медиаблок также сжимается до нуля. Это наблюдение браузера, а не предположение по CSS.

Исправление: запретить сжатие карточек и медиаблоков, правильно ограничить и прокручивать контейнер списка, отдельно определить высоту мобильной карточки. [Скриншот](02-map-desktop.jpg).

### U2 — P1: кнопка звонка открывает `tel:+`

[Выражение формирования телефона](D:/Projects/sigamiz/frontend/map.html:725) содержит лишнее экранирование `\\d` внутри regex literal. Оно удаляет цифры. В браузере `href` кнопки «Telefon qilish» оказался **`tel:+`**.

Исправление: нормализовать телефон одной общей функцией и проверять итоговый номер. Основное действие карточки требует отдельной проверки реального `href`.

### U3 — P1: публикация без координат останавливается без сообщения

[Скрытые поля lat/lng](D:/Projects/sigamiz/frontend/publish.html:45) имеют `required`, а контейнер скрыт через `display:none`. После заполнения всех видимых обязательных полей и нажатия публикации браузер блокирует submit на этих полях. Поэтому [проверка с понятным notice](D:/Projects/sigamiz/frontend/publish.html:233) не выполняется. Подтверждено: `lat` и `lng` были invalid и невидимы, notice остался пустым.

Исправление: скрытые координаты не должны участвовать в недоступной пользователю нативной валидации. Проверять видимый шаг выбора места, показывать ошибку рядом с ним и переводить туда фокус. [Скриншот после нажатия](05-publish-mobile.jpg).

### U4 — P1 для доступности: окно объявления не управляет фокусом

[Окно](D:/Projects/sigamiz/frontend/map.html:700) не имеет роли dialog, фокус после открытия остаётся на BODY. Следующий Tab уводит на кнопку под затемнением; Escape не закрывает окно. [closeDetail](D:/Projects/sigamiz/frontend/map.html:776) не возвращает фокус к открывшему элементу. Кнопка закрытия не имеет доступного названия и имеет размер 40×40 px.

Исправление: полноценное модальное окно с названием, переводом и удержанием фокуса, Escape, восстановлением фокуса и понятной кнопкой закрытия. Кликабельные `article` на карте и главной также заменить доступными ссылками/действиями; сейчас они сами не входят в Tab-порядок.

### U5 — P2: подробности объявления имеют горизонтальное переполнение

На 360 px у `.detail` ширина содержимого **394 px** при доступных **309 px**. Строка автора и сроков растягивает flex-контент, появляется горизонтальный скролл внутри окна. [Автор](D:/Projects/sigamiz/frontend/map.html:390), [CSS](D:/Projects/sigamiz/frontend/map.html:125). [Скриншот](04-detail-mobile.jpg).

Исправление: `min-width:0` на правильном flex-потомке, перенос/усечение длинной строки, не помещать имя, username и два срока в одну неразрывную строку.

### U6 — P2: ценники на Leaflet-карте не вмещают цену

[L.divIcon](D:/Projects/sigamiz/frontend/map.html:652) создаётся без размеров. В браузере корень маркера — 12 px, внутренний pin — 28 px при ширине содержимого 47 px. Цена выходит за зелёный фон. Проблема видна на обоих размерах экрана.

Исправление: задать корректную ширину/якорь и intrinsic sizing ценника. Проверять оба провайдера карты; Yandex в этом запуске не был включён.

### U7 — P1: сбой API выглядит как новые настоящие объявления

[Карта](D:/Projects/sigamiz/frontend/map.html:512) и [главная](D:/Projects/sigamiz/frontend/landing.html:269) подставляют `DEMO_LISTINGS` при любой ошибке API. При искусственном HTTP 500 появились два варианта с username и контактами; предупреждения о сбое или тестовых данных не было. На карте они подписаны как новые объявления. [Скриншот](07-api-failure-demo.jpg).

Исправление: убрать автоматическую демонстрационную подмену из рабочего режима, показать сообщение и повтор загрузки. Деморежим должен быть отдельным и явно обозначенным.

### U8 — P2: пустое избранное выглядит как незагрузившаяся страница

[render([])](D:/Projects/sigamiz/frontend/favorites.html:183) просто очищает содержимое. У вошедшего тестового пользователя виден большой пустой экран и всё ещё кнопка «Войти через бота». Нет объяснения, что избранное пусто, и действия «Открыть карту». [Скриншот](06-favorites-empty.jpg).

Исправление: отдельные состояния загрузки, ошибки, пустого списка и входа; скрывать вход после успешной авторизации, давать переход к выбору объявлений.

### Дополнительные UX-проблемы — P2

- Цена хранится как цена **на человека**, а [карта](D:/Projects/sigamiz/frontend/map.html:677) пишет только `/oy` и `/oyiga`. Уточнить «за человека в месяц» на карточке, подробностях и сравнении.
- [Карточка главной](D:/Projects/sigamiz/frontend/landing.html:261) ведёт на общую карту без ID выбранного объявления. Человек теряет выбранный вариант. Использовать существующий маршрут `?listing=<id>`.
- «Последние объявления» выбираются через `slice(0,6)`, а API не сортирует по дате. Добавить стабильный `ORDER BY created_at DESC, id DESC`; не менять глобальный счётчик активных объявлений при переключении локальных фильтров.
- Загружается до пяти фотографий, но [подробности](D:/Projects/sigamiz/frontend/map.html:706) показывают только первую. Нужны миниатюры/переключение и счётчик фотографий.
- Пол и количество искомых соседей отсутствуют в подробностях, хотя введены при публикации. Это существенные условия выбора жилья; их следует показывать рядом с ценой и числом комнат.
- Навигация различается по страницам; на большинстве мобильных экранов `.nav` скрывается без замены меню. На главной меню есть. Нужен один набор доступных переходов.
- Узбекские тексты смешаны с английскими `Map`, `About`, `Add Listing`, `How it works` и русским `Izbrannoe`; About преимущественно англоязычный. Выбрать язык интерфейса либо сделать явное переключение.
- Форму публикации и управление своими объявлениями приходится проходить в разных каналах: сайт показывает статус, а удалить/продлить можно только в боте. Если это продуктовое решение, дать явные действия перехода к конкретному объявлению в боте. Статусы `hidden_pending_review` и `active` заменить понятными пользователю подписями.
- [Загрузка выдачи](D:/Projects/sigamiz/frontend/map.html:506) не отменяет предыдущий запрос и не проверяет его актуальность. При быстром переключении фильтров поздний ответ старого запроса может заменить актуальный набор. Клиентский `matches` отсекает лишнее, но не возвращает варианты, отсутствовавшие в старой выдаче. Нужны AbortController или номер актуального запроса. Это вывод по коду; задержки ответов для воспроизведения не моделировались.
- На мобильной карте фильтры до выбора представлены только иконками; подписи раскрываются на hover/focus/active. Для основных условий поиска полезнее постоянные короткие подписи.
- Форма теряет черновик при перезагрузке или переходе между страницами. Добавить сохранение черновика и подтверждение ухода при несохранённых изменениях.

## Как разделить код после исправления ошибок

Оба канала должны вызывать один набор операций: `publish_offer`, `search_offers`, `save_search_preferences`, `report_listing`, `review_listing`, `extend_listing`, `remove_listing`. Внутри этих операций находятся бан, ограничения количества, публичные координаты, допустимые статусы, правила поиска и событие уведомления.

Боту оставить диалог и Telegram-клавиатуры. FastAPI — HTTP, проверку сессии и преобразование ответа. SQL и транзакции сосредоточить в репозиториях данных, схему — в миграциях. Отправку сообщений и хранение фото вынести за границы бизнес-правил.

Для текущего статического сайта достаточно общих `auth.js`, `api.js`, `listing-ui.js`, справочников и CSS-переменных/компонентов. Начать с общего авторизационного состояния, карточки объявления и навигации. Полная смена frontend-фреймворка сама по себе перечисленные ошибки не устранит.

Порядок работ: B15/B1/B2/B3/B4 и U1/U2/U3/U7 → надёжность PostgreSQL и фото → общий поиск/уведомления/статусы → общие frontend-модули → галерея, сравнение, единый язык и навигация.

## Проверки и пределы аудита

Воспроизведены в изоляции: подтверждение токена чужого инициатора и выдача ему сессии другого пользователя в fallback-входе; публикация забаненным пользователем; сохранение точных координат; совпадение фото с собственным объявлением; неверные переходы removed/hidden в expired; принятие NaN; потеря параллельного изменения черновика. Сопоставление AST подтвердило идентичность двух matching-функций и отсутствие вызовов старых фото-функций из публикации.

В браузере измерены размеры карточек, маркеров и переполнение окна; проверены Tab/Escape, телефонная ссылка, публикация без координат, пустое избранное и HTTP 500. Скриншоты находятся рядом с этим отчётом.

Не проверены: реальная авторизация Telegram, доставка сообщений настоящим пользователям, взаимодействия Telegram-клиента, конкуренция и миграции на живом PostgreSQL, Yandex Maps, конфигурация продакшена, полноценный axe/NVDA аудит, показатели скорости и контраста. Мобильная проверка — изменение viewport, без реальной экранной клавиатуры и системного permission flow.

Не отмечены как ошибки: отсутствие rollback избранного — откат уже есть; очистка формы на ошибке — `reset()` вызывается только после успешной публикации; размер кнопки аккаунта — измеренные 44×44 px; горизонтальный скролл всего мобильного документа — его не было. Отсутствие фото у локальных тестовых объявлений не трактовалось как доказательство поломки загрузки фото в продакшене.

Использованы `ui-design` в режиме Audit и `ui-verification` для конкретных находок. Прочитаны `references/feature-playbooks.md`, `references/ship-readiness.md`, `references/output-adapters.md`, `rules/_sections.md`, правила `forms-no-disable-while-submitting`, `focus-broken-focus-trap`, `states-no-error-state`, `interaction-keyboard-operable`, `layout-long-content-safety`, `async-out-of-order-responses`, `states-no-empty-state`, `interaction-target-size`, а также `ui-verification/references/session-setup.md`. Дизайн-руководства Build/Direction не использовались. Исходный код приложения в ходе аудита не изменялся.
